# エキログ 実装企画書（Claude Code向け）

Nov 16, 2026 · @紅茶

## 1. 概要

エキログは、行った駅を記録して、日本地図・路線・市区町村が埋まっていくのを楽しむスマホアプリです。iPhoneとAndroidの両方に、1つのコードベースから出します。画面は[デザインキャンバス](https://claude.ai/artifact/UrZZ88X5EVxiMETawq1X8U)の11画面が正です。

- **コンセプト**：行った駅が、自分だけの鉄道地図になる
- **想定ユーザー**：旅行や乗り鉄が好きな人、毎日の移動もついでに残したい人。細かい管理より、気軽さと振り返る楽しさを優先する
- **差別化の3本柱**：過去の訪問をすぐ埋められる（まとめて登録・写真から記録）／記録の手間がない（自動チェックイン）／見て楽しい（各社に寄せたナンバリング、市区町村の制覇）

| 既存アプリ | 中心にある機能 | エキログが足すもの |
| --- | --- | --- |
| [乗り鉄撮り鉄](https://apps.apple.com/JP/app/id588715574) | 訪問日時・写真・メモ、路線ごとの達成率 | 自動チェックイン、写真からの過去記録 |
| [ekinote](https://apps.apple.com/jp/app/id1588324446) | 駅チェックインと駅周辺の街情報 | 路線・市区町村の制覇、ナンバリング表示 |
| [エキタグ](https://apps.apple.com/jp/app/id1672193381) | NFCタグでの駅スタンプ（対象駅のみ） | 全駅が対象、現地に行かずに過去分も登録 |

**目標（案）**：初回起動から最初の記録まで1分以内。初日のうちに、まとめて登録で20駅以上が埋まる。

## 4. 機能仕様

各機能の動きと、完成とみなす条件（受け入れ条件）です。Claude Codeにはこの受け入れ条件をそのまま渡します。数値はすべて初期値の案で、実機で試して調整します。

### 4.1 駅を記録する

- 現在地から近い駅を3件、距離つきで出す。駅名・ひらがな・路線名の検索でも選べる
- 記録の種類は「降りた／乗り換え／通過」。日付（初期値は今日）、メモ、写真（最大10枚）を付けられる
- その日に駅の近くで撮った写真があれば、添付候補として出す
- 受け入れ条件：位置情報がオフでも検索から記録できる。圈外でも記録でき、再起動しても残る

### 4.2 路線からまとめて登録

- 路線の駅をナンバリング順に路線図の形で並べる。未訪問の駅をタップして複数選び、まとめて登録する（日付なしでも可）
- 受け入れ条件：選んだ瞬間に達成率のバーに反映され、登録後は「訪問済み」に変わる

### 4.3 写真から記録

- ユーザーが選んだ写真だけを読み、撮影位置から半径300m以内の最寄り駅を推定する
- 同じ日・同じ駅の写真は1件の候補にまとめる。記録済みの駅なら「写真だけ追加」にする
- 位置情報のない写真は、自分で駅を選んで追加する
- 受け入れ条件：写真を100枚選んでも、10秒以内に候補が出る

### 4.4 達成状況（都道府県・市区町村・路線）

- 都道府県：47のタイル地図を、訪れた駅の数で4段階に塗る
- 市区町村：駅のある市区町村だけを分母にする（例：東京都は50）
- 路線：訪れた駅数／全駅数。全駅を訪れたら「制覇」
- 「通過」を達成に数えるかは設定で選べる（初期値は数えない）

### 4.5 駅ナンバリングの表示

- 1つの駅に複数のナンバリングを持てる（新宿は10）。一覧では2つまで出し、残りは「+8」のように省略する
- 形・色・書体は事業者ごとの設定表で決める。路線記号から自動で判定し、駅データ側で個別に上書きもできる
- ナンバリングのない駅にはバッジを出さない
- 受け入れ条件：設定表を1か所直すと、全画面のバッジに反映される

### 4.6 通知

- 自動チェックインで駅を見つけたら通知する。「記録する／乗り換え／記録しない」のボタンで、アプリを開かずに確定できる
- 通過した駅は1通にまとめる。「すぐに記録」の設定では、確認なしで記録して結果だけ知らせる
- 移動中はロック画面に路線と到着駅を出す（iPhoneはライブアクティビティ、Androidは常駐通知）。v1.1で入れる

## 5. 自動チェックインの判定

OSのジオフェンス（駅の周りに引いた円）で「駅に近づいた」ことだけを省電力で検知し、近づいたときだけ数分間細かく位置を取って種類を決めます。同時に見張れる円の数に上限があるため、全国の駅を一度には監視できません。

|  | iPhone | Android |
| --- | --- | --- |
| 同時に監視できる円 | 1アプリ20か所まで（[参考](https://docs.sentiance.com/sdk/appendix/ios/ios-region-monitoring)） | 1アプリ100か所まで（[公式](https://developer.android.com/training/location/geofencing)） |
| 必要な許可 | 位置情報「常に」。「使用中のみ」ではバックグラウンドで届かない（[参考](https://capgo.app/blog/capacitor-geofences-not-triggering-ios/)） | 位置情報「常に許可」 |
| 反応の速さ | OSの都合で遅れることがある | Android 8.0以降は、バックグラウンドでは数分おきに反応（[公式](https://developer.android.com/training/location/geofencing)） |

**監視する駅の選び方**：現在地に近い駅から上限まで（iPhoneは19駅＋外枠1つ、Androidは99駅＋外枠1つ）を登録します。外枠＝その駅たちを囲む大きな円を抜けたら、新しい現在地で選び直します。駅の円は半径150mから始め、地下駅は広めにします。

| 状況（初期値の案） | 判定 |
| --- | --- |
| 駅から150m以内に5分以上とどまった | 降りた |
| 駅で止まったが5分未満で、出発後の向きが別の路線 | 乗り換え |
| 時速20km以上のまま駅の近くを通り過ぎた | 通過 |
| 除外する駅／同じ駅を30分以内に再び検知 | 記録しない |

判定結果はまず「候補」として保存し、設定に応じて通知で確認するか、そのまま記録します。通過の検知はジオフェンスの遅れで取りこぼしやすいため、MVPでは「降りた・乗り換え」だけを自動にし、通過はv1.1で移動中の連続測位と合わせて入れます。

## 6. 技術構成

Expo（React Native＋TypeScript）で作り、データはすべて端末内のSQLiteに置きます。MVPではサーバーを持ちません。TypeScriptはClaude Codeが型を手がかりに安全に直しやすく、1つのコードでiPhoneとAndroidの両方を出せるからです。

| 役割 | 使うもの | メモ |
| --- | --- | --- |
| アプリ本体 | Expo SDK 58、TypeScript、Expo Router | 開発ビルドで動かす。Expo GoではiOSのバックグラウンド実行が動かない（[TaskManager](https://docs.expo.dev/versions/v54.0.0/sdk/task-manager/)） |
| 端末内DB | expo-sqlite＋Drizzle ORM | 駅マスタは同梱のSQLite、記録は別のDBに分ける |
| 位置情報・ジオフェンス | expo-location＋expo-task-manager | バックグラウンドでの位置更新とジオフェンスの両方に対応（[公式](https://docs.expo.dev/versions/latest/sdk/location.md)） |
| 通知 | expo-notifications | ボタン付きの通知（通知カテゴリ）で「記録する／乗り換え／記録しない」 |
| 写真 | expo-media-library | 写真の撮影位置を取得。Androidは ACCESS\_MEDIA\_LOCATION 権限が必要（[公式](https://docs.expo.dev/versions/v58.0.0/sdk/media-library-legacy/)） |
| ロック画面の表示 | expo-widgets | SDK 56で安定版になった（[Expoブログ](https://expo.dev/blog/ios-widgets-and-live-activities-in-expo)）。ライブアクティビティはiOSのみ（[公式](https://docs.expo.dev/versions/latest/sdk/widgets/)） |
| 近い駅の検索 | 端末内の空間インデックス（kdbush） | 全国の駅から近い順を即座に出す。写真の駅推定も同じ仕組み |
| フォント | expo-font | Geologica、Noto Sans JP、ナンバリング用の代替書体（Jost、Hind、Barlowなど） |
| テスト | Jest、Maestro | 判定ロジックは単体テスト、画面の流れはMaestroで通して確認 |

ロック画面での移動中表示は、iPhoneはライブアクティビティ、Androidは常駐通知で作ります。ライブアクティビティはアプリ内から更新できるため、v1.1でもプッシュ通知用のサーバーは不要です。

## 7. データ設計

駅マスタは国のオープンデータからビルド時に作ってアプリに同梱し、ユーザーの記録とは別のDBに分けます。駅マスタを更新しても、記録は消えません。

### 7.1 データの出典

| データ | 出典 | ライセンス | 使い方 |
| --- | --- | --- | --- |
| 駅・路線・運営会社 | [国土数値情報 鉄道データ（N02）](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N02-2024.html) | 2020年以降のデータはCC BY 4.0 | 駅名・路線名・運営会社・座標を使う。「グループコード」（300m以内の同名の駅をまとめたもの）で乗換駅を1駅にまとめる |
| 市区町村 | [国土数値情報 行政区域（N03）](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N03-2025.html) | CC BY 4.0 | ビルド時に駅の座標から市区町村コードを付ける。境界の形はアプリに入れない |
| 駅ナンバリング・路線記号・路線色 | 自前のCSV（各社の公式資料をもとに作る） | 要確認 | N02には含まれない。東京メトロなど、[公共交通オープンデータセンター](https://www.odpt.org/)のデータに駅コードがある事業者もある |
| 駅名の読みがな | 未定 | 要確認 | ひらがな検索に使う。N02には含まれない |

CC BY 4.0 のデータは出典の表示が条件なので、アプリ内に「データの出典」画面を作ります。

### 7.2 テーブル

| テーブル | 主な列 | 役割 |
| --- | --- | --- |
| operators | id, name, badge\_style, badge\_font | 事業者と、ナンバリングの形・書体 |
| lines | id, operator\_id, name, code, color, is\_loop | 路線と路線記号・路線色 |
| stations | id, name, kana, lat, lng, pref\_code, muni\_code | 駅。N02のグループコード単位で、新宿は1駅 |
| station\_lines | station\_id, line\_id, number, seq | 駅と路線の対応。ナンバリング番号と路線内の並び順 |
| municipalities | code, pref\_code, name, has\_station | 市区町村。駅のあるものだけを達成率の分母にする |
| visits | id, station\_id, kind, visited\_on, source, memo, created\_at | 記録。kind＝降りた／乗り換え／通過、source＝手動／まとめて／自動／写真。日付なし可 |
| photos | id, visit\_id, asset\_id, taken\_at, lat, lng | 写真は端末の写真ライブラリのIDだけを持つ |
| auto\_candidates | id, station\_id, detected\_at, kind\_guess, dwell\_sec, status | 自動チェックインの候補（未確認／記録済み／却下） |
| excluded\_stations | station\_id | 自動記録から外す駅 |
| settings | key, value | 設定 |

達成率は保存せず、visitsと駅マスタからその都度SQLで数えます。

## 8. Claude Codeでの進め方

この企画書をリポジトリに `docs/SPEC.md` として置き、マイルストーンを1つずつ「計画→実装→検証」で進めます。1マイルストーン＝1セッションで、終わったら `/clear` します。各手順は公式の[ベストプラクティス](https://code.claude.com/docs/en/best-practices.md)に沿っています。

### 8.1 最初の準備

1. Expoのプロジェクトを作り、gitで管理する
2. `docs/` に、この企画書（SPEC.md）、デザインキャンバスから書き出した各画面の画像（design/）、ナンバリングの表示スタイル表を置く
3. `/init` でCLAUDE.mdの土台を作り、下の例の内容まで削る
4. フックで、ファイル編集のたびに型チェックとlintを必ず走らせる（CLAUDE.mdの指示と違い、フックは毎回確実に動く）

### 8.2 CLAUDE.md の例

CLAUDE.mdは毎回読み込まれるので短く保ちます。仕様書は `@` で取り込まず、場所だけ書いて必要なときに読ませます。

```markdown
# エキログ
- 仕様: docs/SPEC.md ／ 画面: docs/design/*.png

# コマンド
- 型チェック: npm run typecheck
- テスト: npm test -- <ファイル>
- 起動: npx expo run:ios （開発ビルド。Expo Goは使わない）
- 駅マスタの再生成: npm run build:master

# ルール
- 画面の文字はGeologica、日本語はNoto Sans JP
- 駅ナンバリングは NumberingBadge だけで描く。形・色・書体は src/data/operatorStyles.ts の表で決める
- assets/db/stations.db は手で編集しない（スクリプトで作り直す）
- 記録DBの変更は必ずマイグレーションで行う
- 自動チェックインの判定は src/auto/ に置き、変えたら必ずテストを足す
```

### 8.3 マイルストーン

| # | 作るもの | 完了条件（Claudeに走らせるチェック） |
| --- | --- | --- |
| M0 | 土台：Expo・TypeScript・Expo Router・Drizzle・フォント、タブ5つの空の画面 | 型チェックとテストが通る。iPhoneとAndroidの開発ビルドが起動する |


## 9. テストと品質

判定ロジックとデータは自動テストで守り、位置情報と通知は実機でしか確かめられないので、下の確認表で確かめます。

**自動テスト**

- 単体テスト（Jest）：自動チェックインの判定（位置の記録データを入れ、種類が出るか）、達成率の計算、写真からの駅の推定、ナンバリングの表示スタイルの判定
- 駅マスタの検査：作り直すたびに、件数・重複・座標の範囲・市区町村コードの欠けを調べる
- 画面のE2Eテスト（Maestro）：記録、まとめて登録、写真から記録、設定の切り替え

**実機での確認（リリース前に毎回）**

- [ ] 位置情報が「使用中のみ」のとき、自動チェックインが使えない理由を説明し、設定へ案内する
- [ ] アプリを閉じた状態で駅に着き、通知が届く（iPhone・Android）
- [ ] 通知のボタンで記録でき、アプリを開くと反映されている
- [ ] 地下駅と圈外の駅で記録できる
- [ ] 自動チェックインをオンにした日とオフの日で、電池の減りを比べる
- [ ] 写真の権限を「選んだ写真のみ」にしても、写真から記録が使える
- [ ] 「データの出典」画面に国土数値情報の出典が出ている
- [ ] ナンバリングの表示を、各社の公式資料と見比べる

## 10. リスクと未決事項

いちばん大きいリスクは自動チェックインの精度と電池です。M6より前に、判定だけを入れた試作を実機で1週間使って確かめるのが安全です。

| リスク | 起きること | 対策 |
| --- | --- | --- |
| 自動チェックインの精度 | 地下駅・通過・通知の遅れで、誤記録や取りこぼし | 初期設定は「確認してから記録」。通過の自動検知はv1.1 |
| 電池の消費 | 自動チェックインを切られる | 細かい測位は駅の近くの数分だけ。省電力モードを用意 |
| バックグラウンド位置情報のストア審査 | 用途の説明を求められ、申請が遅れる | 許可を求める前の説明画面を作る。「常に許可」なしでも他の機能はすべて使える |
| ナンバリングのデザイン | 各社の意匠や商標に触れるおそれ | 公開前に各社へ確認。必要なら表の切り替えだけで共通の形に戻せる |
| 駅データの更新 | N02の駅コードは緯度順の通し番号なので、新駅ができると番号がずれる（[N02](https://nlftp.mlit.go.jp/ksj/gml/datalist/KsjTmplt-N02-2024.html)） | アプリ独自の駅IDを振り、更新のたびに駅名・路線・座標で対応を取る |

**未決事項**

- ナンバリングCSVの作り方：公共交通オープンデータセンターから取る事業者と、手で入れる事業者の範囲。それぞれの利用条件
